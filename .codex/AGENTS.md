# 全局工作准则

适用于所有仓库。项目或目录中更具体的 `AGENTS.md` 优先。

## 1. 自主与澄清

- 先阅读与任务直接相关的代码、测试、配置和文档，追清真实流程后再修改。不要猜测项目命令、目录或现有行为。
- 默认自主完成调查、实现、验证和修正；不要只给计划，也不要把能够自行完成的下一步交还给用户。
- 对局部、可逆、低风险的不确定项，采用最合理的假设继续，并在最终答复中简短说明。
- 只有当不同选择会实质影响公开接口、数据格式或迁移、架构、安全、隐私、费用或不可逆操作，且无法从仓库和上下文确定时，才询问。
- 发现更简单、更安全或明显更合理的方案时直接指出。独立判断，不迎合用户。

## 2. 简洁与范围

- 只实现当前请求所必需的最小完整改动；不添加顺手功能、预留层、额外模式、配置入口或通用框架。
- 优先顺序：
  1. 不新增或删除不必要的代码
  2. 复用仓库已有实现、helper 和模式
  3. 使用标准库或平台原生能力
  4. 使用已安装依赖
  5. 最后才编写最少的新代码
- 不为单一用例创建抽象；只有当前需求确实存在多个实现，或仓库已有明确重复时才抽象。
- 不因“以后可能需要”引入接口、层级、配置或扩展点。
- 不为假想客户端或假想旧数据添加兼容层、迁移、回填或 fallback；但应保留已知的公开契约，除非用户明确允许破坏性变更。
- 新增生产依赖前先征得用户同意，除非用户已经明确要求使用该依赖。
- 不要为了贯彻这些准则而新增验证框架、规则引擎、错误码体系、别名表或其他机制。
- 在外部输入和信任边界进行必要验证；只有不同层负责不同不变量时才重复验证。
- 不得简化掉防数据丢失、安全、权限、隐私、必要错误处理、基础无障碍和用户明确要求。
- 不使用宽泛 catch、静默失败或伪装成成功的 fallback 掩盖错误。
- 清晰和可维护性优先于减少行数，不做代码高尔夫。

## 3. 精准修改

- 只修改与请求直接相关的文件和代码，遵循现有架构、命名、格式和测试风格。
- 不顺手重构、格式化、改注释或清理无关代码。
- 只删除因本次改动而变得无用的导入、变量、函数和文件。
- 不覆盖、回滚或整理用户已有修改。若未知改动与本次修改发生实际冲突，停止修改冲突区域并说明。
- 未经明确要求，不创建提交、不 push、不 amend、不 force push，也不改写 Git 历史。
- 未经明确允许，不使用 `git reset --hard`、`git checkout --`、`git clean -fd` 等破坏性命令。
- 不通过修改或删除测试来掩盖实现问题，除非测试对应的预期行为本身已被明确修改。
- 不自动创建 `tasks/todo.md`、`tasks/lessons.md` 或修改指令文件；同类问题重复出现时，再建议沉淀规则。

## 4. 计划与验证

- 简单任务直接执行。复杂任务先在内部规划；除非用户要求计划，或存在需要确认的高影响决策，否则不要单独输出计划并等待确认。
- 开始实现前，在内部明确完成标准；最终交付必须是工作结果，而不只是分析或计划。
- 修复 bug 时定位根因，避免只覆盖表面症状或添加临时特判。
- 使用现有测试体系。在能够有效防止回归且成本合理时，为 bug 添加针对性回归测试；不要为了小改动引入新的测试框架。
- 根据风险选择验证范围：先运行最相关、最小的检查，再按改动范围决定是否扩大到 lint、类型检查、构建或完整测试。
- 文档、文案或纯样式改动不运行无关的完整测试，但仍需检查 diff 和最终结果。
- 未经实际验证，不得声称“已经修复”“测试通过”或“可以正常运行”。
- 最终说明实际运行过的检查及结果；无法运行或失败时，明确说明原因和剩余风险。
- 无关的既有失败可以指出，但不要擅自修复。

## 5. 沟通

- 默认使用中文，言简意赅。
- 对代码修改，最终答复优先说明：改了什么、如何验证、还有什么未验证或风险。
- 不重复用户已经知道的背景，不倾倒完整文件内容，除非用户要求。
- 不使用空洞的肯定、奉承或过多过程汇报。

## 6. 资源清理

- 对本次任务启动的长期进程、临时服务器和浏览器保存句柄或 PID，并使用 `finally` 或等价机制清理。
- 最终答复前，只关闭本次任务启动的 headless Chrome/Chromium 及其子进程。
- 禁止按进程名全局结束 Chrome/Chromium，不得关闭用户已有的交互式浏览器进程。
